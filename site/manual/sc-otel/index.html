sc-otel

Submit logs, spans, metrics, and profiles through a durable local queue to an OTLP collector. Delivery is at least once: retained records can be resent after interrupted or uncertain delivery.

Usage: sc-otel [OPTIONS] <COMMAND>

Commands:
  emit      Validate and durably admit telemetry, then attempt delivery
  validate  Validate input locally without opening a store or contacting a collector
  flush     Attempt delivery of pending records in the configured durable store
  status    Inspect the queue summary or selected submissions/record keys
  help      Print this message or the help of the given subcommand(s)

Options:
      --config <CONFIG>
          Read telemetry YAML from this explicit path. No configuration file is auto-discovered. Relative store.path values in YAML are resolved against this file's directory. validate does not load configuration

      --store <STORE>
          Use this `SQLite` queue path instead of store.path in YAML. Required for emit, flush, and status unless supplied in the file; no environment fallback. Relative CLI paths use the current directory

      --endpoint <ENDPOINT>
          Override the OTLP HTTP base URL. Precedence: this flag, otlp.endpoint in YAML, `OTEL_EXPORTER_OTLP_ENDPOINT`, then <http://localhost:4318>

      --output <OUTPUT>
          Choose machine-readable JSON (default) or one compact text result line. Parser errors and help use Clap's normal diagnostics regardless of this setting
          
          [default: json]
          [possible values: json, text]

  -h, --help
          Print help (see a summary with '-h')

  -V, --version
          Print version

QUICK START
  sc-otel validate --log '{"body":"started"}'
  sc-otel --store queue.sqlite emit --log '{"body":"started"}' --no-flush
  sc-otel --store queue.sqlite status
  sc-otel --store queue.sqlite --endpoint http://localhost:4318 flush --timeout 10

  validate is local and needs no store or collector. emit, flush, and status
  require a store path. Use the same store across invocations to retain queued
  records. --no-flush reports durable admission, not confirmed delivery.

INPUT
  Pass --stdin with one complete JSON document, for example event.json:
    {"version":1,"logs":[{"body":"started"}]}
  Then run:
    sc-otel validate --stdin < event.json

  Alternatively use --log, --span, --metric, or --profile with inline JSON or
  @FILE. Fragment mode supplies version 1. Logs, spans, and metrics accept
  repeated flags; each argument is one point/stream, not an array. Profiles
  use one object. --stdin and fragment flags are mutually exclusive.
  Input follows SubmissionInput, not raw OTLP protobuf JSON. The normalized
  envelope contains system-generated identifiers and timestamps.

CONFIGURATION
  Supply --config telemetry.yaml explicitly; no file is auto-discovered.
  Minimal example:
    service: example-service
    otlp:
      endpoint: http://localhost:4318
      timeout_ms: 10000
    store:
      path: ./queue.sqlite

  CLI --store and --endpoint override YAML. YAML service and otlp.endpoint
  override OTEL_SERVICE_NAME and OTEL_EXPORTER_OTLP_ENDPOINT respectively.
  Without either, service is unknown_service and endpoint is
  http://localhost:4318. SC_OTEL_AUTH_HEADER supplies the authentication header;
  keep secrets out of command arguments and shell history. No store-path
  environment fallback exists. YAML store.path is relative to the YAML file;
  --store and @FILE paths are relative to the current working directory.

  Additional store YAML keys: max_bytes, disk_bound_policy, and
  delivered_retention_hours. validate never loads this configuration.

OUTPUT AND AUTOMATION
  --output json (default) prints one sc-otel.result/v1 object for an executed
  command. Fields: schema, command, exit_code, state, receipt, flush, status,
  envelope, error. Non-applicable fields are null. A validation success includes
  envelope; an admitted emit includes receipt; flush/status include their report.
  Errors include code, message, cause, and remediation. Use exit_code and error.code
  for automation rather than parsing human-readable text.

  --output text prints: <state> exit=<n> [submission=<id>] [error=<code>].
  States: validated, status, rejected, admitted_pending, admitted_delivered,
  admitted_failed. Clap usage errors and --help/--version are exceptions to the
  JSON result format. Unexpected internal errors may write diagnostics to stderr.

EXIT CODES
  0  Success (with emit --no-flush: admitted, not necessarily delivered).
  1  Unexpected internal failure.
  2  Command-line usage error; inspect stderr and --help.
  3  Invalid submission input; inspect error.code and remediation.
  4  Invalid/missing configuration or an unsupported combination.
  5  Admission/client failure; inspect receipt to determine whether admission occurred.
  6  Admitted delivery remains pending; preserve the store and retry flush.
  7  Terminal delivery failure; inspect the report and retained record.

DELIVERY AND RECOVERY
  Delivery is at least once, not exactly once. Use a stable record_key when
  deduplication is needed. Preserve the durable store after uncertain delivery;
  deleting it discards pending telemetry. Fix configuration/collector errors
  before retrying. Do not treat admission or local validation as collector receipt.

DOCUMENTATION
  Run sc-otel <command> --help for detailed options and examples.
  The Markdown manual and website reference are generated from this same Clap
  help at every release; their version is the CLI package version.

sc-otel emit

Parse and validate the input, open the configured durable store, and admit the submission before delivery. Normally flushes this submission and shuts down the client; --no-flush returns after admission. A receipt identifies admitted records even if delivery later fails.

Usage: sc-otel emit [OPTIONS] <--stdin|--log <JSON|@FILE>|--span <JSON|@FILE>|--metric <JSON|@FILE>|--profile <JSON|@FILE>>

Options:
      --config <CONFIG>
          Read telemetry YAML from this explicit path. No configuration file is auto-discovered. Relative store.path values in YAML are resolved against this file's directory. validate does not load configuration

      --stdin
          Read one complete `SubmissionInput` JSON document from stdin. Cannot combine with fragment flags. Requires version: 1; use `record_key` inside the document for deduplication

      --log <JSON|@FILE>
          Append one log point as inline JSON or @FILE. Repeat to submit multiple logs; can combine with other fragment types

      --store <STORE>
          Use this `SQLite` queue path instead of store.path in YAML. Required for emit, flush, and status unless supplied in the file; no environment fallback. Relative CLI paths use the current directory

      --endpoint <ENDPOINT>
          Override the OTLP HTTP base URL. Precedence: this flag, otlp.endpoint in YAML, `OTEL_EXPORTER_OTLP_ENDPOINT`, then <http://localhost:4318>

      --span <JSON|@FILE>
          Append one span point as inline JSON or @FILE. Repeat to submit multiple spans; can combine with other fragment types

      --metric <JSON|@FILE>
          Append one metric stream as inline JSON or @FILE. Repeat for multiple streams; can combine with other fragment types

      --output <OUTPUT>
          Choose machine-readable JSON (default) or one compact text result line. Parser errors and help use Clap's normal diagnostics regardless of this setting
          
          [default: json]
          [possible values: json, text]

      --profile <JSON|@FILE>
          Supply the profiles object as inline JSON or @FILE. May be combined with log, span, and metric fragments

      --record-key <RECORD_KEY>
          Deduplicate a fragment-mode submission with this caller-owned key. With --stdin, put `record_key` in the JSON document instead

      --no-flush
          Return after durable admission without initiating a flush. Exit 0 confirms admission only, not delivery; retain the store and later run flush

  -h, --help
          Print help (see a summary with '-h')

Examples:
  sc-otel --store queue.sqlite emit --log '{"body":"started"}' --no-flush
  sc-otel --config telemetry.yaml emit --stdin < event.json
  sc-otel --store queue.sqlite emit --log @log.json --record-key job-42

Use --stdin OR fragment flags; at least one input source is required. With stdin, a record_key belongs inside the input JSON. Keep the store after exit 6 so flush can retry delivery.

sc-otel validate

Parse SubmissionInput and construct a normalized SubmissionEnvelope, including generated identifiers and timestamps. The JSON result includes the normalized envelope. This checks input shape and values, not collector availability or successful delivery; global configuration flags are not loaded.

Usage: sc-otel validate [OPTIONS] <--stdin|--log <JSON|@FILE>|--span <JSON|@FILE>|--metric <JSON|@FILE>|--profile <JSON|@FILE>>

Options:
      --config <CONFIG>
          Read telemetry YAML from this explicit path. No configuration file is auto-discovered. Relative store.path values in YAML are resolved against this file's directory. validate does not load configuration

      --stdin
          Read one complete `SubmissionInput` JSON document from stdin. Cannot combine with fragment flags. Requires version: 1; use `record_key` inside the document for deduplication

      --log <JSON|@FILE>
          Append one log point as inline JSON or @FILE. Repeat to submit multiple logs; can combine with other fragment types

      --store <STORE>
          Use this `SQLite` queue path instead of store.path in YAML. Required for emit, flush, and status unless supplied in the file; no environment fallback. Relative CLI paths use the current directory

      --endpoint <ENDPOINT>
          Override the OTLP HTTP base URL. Precedence: this flag, otlp.endpoint in YAML, `OTEL_EXPORTER_OTLP_ENDPOINT`, then <http://localhost:4318>

      --span <JSON|@FILE>
          Append one span point as inline JSON or @FILE. Repeat to submit multiple spans; can combine with other fragment types

      --metric <JSON|@FILE>
          Append one metric stream as inline JSON or @FILE. Repeat for multiple streams; can combine with other fragment types

      --output <OUTPUT>
          Choose machine-readable JSON (default) or one compact text result line. Parser errors and help use Clap's normal diagnostics regardless of this setting
          
          [default: json]
          [possible values: json, text]

      --profile <JSON|@FILE>
          Supply the profiles object as inline JSON or @FILE. May be combined with log, span, and metric fragments

  -h, --help
          Print help (see a summary with '-h')

Examples:
  sc-otel validate --log '{"body":"started"}'
  sc-otel validate --stdin < event.json
  sc-otel validate --log @log.json --span @span.json

Fragment files are UTF-8 JSON, one signal value per file. Repeating --log, --span, or --metric appends values; --profile accepts one profiles object. Do not supply generated envelope fields such as submission_id in SubmissionInput.

sc-otel flush

Attempt delivery of pending records in the configured durable store

Usage: sc-otel flush [OPTIONS]

Options:
      --config <CONFIG>
          Read telemetry YAML from this explicit path. No configuration file is auto-discovered. Relative store.path values in YAML are resolved against this file's directory. validate does not load configuration

      --timeout <SECONDS>
          Bound this flush in whole, unsigned seconds (including 0). Defaults to the resolved flush deadline, currently 30 seconds. Shutdown uses its own configured deadline

      --store <STORE>
          Use this `SQLite` queue path instead of store.path in YAML. Required for emit, flush, and status unless supplied in the file; no environment fallback. Relative CLI paths use the current directory

      --endpoint <ENDPOINT>
          Override the OTLP HTTP base URL. Precedence: this flag, otlp.endpoint in YAML, `OTEL_EXPORTER_OTLP_ENDPOINT`, then <http://localhost:4318>

      --output <OUTPUT>
          Choose machine-readable JSON (default) or one compact text result line. Parser errors and help use Clap's normal diagnostics regardless of this setting
          
          [default: json]
          [possible values: json, text]

  -h, --help
          Print help (see a summary with '-h')

Examples:
  sc-otel --config telemetry.yaml flush --timeout 10
  sc-otel --store queue.sqlite --endpoint http://localhost:4318 flush

This command flushes the store, not one selected submission. Exit 6 means records remain pending; retain the queue and retry when the collector is available. Exit 7 means a terminal delivery failure. A flush deadline is not a wall-clock bound for opening and shutting down the process.

sc-otel status

Inspect the queue summary or selected submissions/record keys

Usage: sc-otel status [OPTIONS]

Options:
      --config <CONFIG>
          Read telemetry YAML from this explicit path. No configuration file is auto-discovered. Relative store.path values in YAML are resolved against this file's directory. validate does not load configuration

      --submission <SUBMISSION>
          Select a submission by UUID; repeat for multiple submissions. Mutually exclusive with --record-key. With neither selector, show a queue summary

      --record-key <RECORD_KEY>
          Select records by caller-owned key; repeat for multiple keys. Cannot combine with --submission

      --store <STORE>
          Use this `SQLite` queue path instead of store.path in YAML. Required for emit, flush, and status unless supplied in the file; no environment fallback. Relative CLI paths use the current directory

      --endpoint <ENDPOINT>
          Override the OTLP HTTP base URL. Precedence: this flag, otlp.endpoint in YAML, `OTEL_EXPORTER_OTLP_ENDPOINT`, then <http://localhost:4318>

      --output <OUTPUT>
          Choose machine-readable JSON (default) or one compact text result line. Parser errors and help use Clap's normal diagnostics regardless of this setting
          
          [default: json]
          [possible values: json, text]

  -h, --help
          Print help (see a summary with '-h')

Examples:
  sc-otel --store queue.sqlite status
  sc-otel --store queue.sqlite status --record-key job-42
  sc-otel --store queue.sqlite status --submission 018f8f5e-5c4c-7abc-8def-0123456789ab

Repeat one selector kind to query multiple records; do not mix --submission with --record-key. This opens the durable client and runs its normal shutdown; it is not an offline, read-only SQLite inspection.
