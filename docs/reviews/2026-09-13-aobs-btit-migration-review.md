# Independent BTIT migration design review

Reviewer: aobs (this review's author). Date: 2026-09-13.

Recommendation: **NO APPROVAL for implementation as currently specified.** The companion-crate architecture and an A5.0 contract-resolution stage are reasonable to proceed with. Re-review the locked contracts before implementing the affected stages. This is a design review, not a claim that the proposed implementation already contains these defects.

Reviewed `docs/phase-A/log-facade-bridge-design.md` and `docs/phase-A/sprint-A5-log-facade-bridge.md` in the `plan/phase-a-log-facade-bridge` worktree at `d3435f6b5b4c4028f040df27bceb17c5dc74b2c8`, against its core implementation and BTIT source at `f6f69dc`. References below use those revisions. The prior Terra-authored material, including its attribution to aobs, is background information only; it is not this author's approval. Every finding below is independently assessed and owned by this author.

1. **P1 — The shutdown contract still permits losing the final result.** Design lines 56–62 define both `Stopping` and `ShutdownTimedOut`, but lines 119–120 leave observation after timeout optional and permit terminal `Stopping`. Sprint lines 158–161 require exactly one final shutdown to be observed. Those alternatives do not satisfy the same contract. Core `runtime.rs:224` consumes the logger and continues waiting after its configured threshold; the BTIT `shutdown_installed` baseline additionally needs sole `Arc` ownership. Merely making control handles read-only does not define how the implementation obtains that ownership, retains final health, or reports a late helper failure.

   Required: specify an owner independent of control-handle lifetimes; admission versus shutdown ordering; who retains the stopped logger/final health; and a control-side completion observation API that survives a consumed guard. Treat a wait timeout separately from actual worker completion. Specify spawn failure and helper panic outcomes. Require tests where a control handle outlives shutdown, a flush times out before shutdown, and the worker later succeeds or fails. Also bound outstanding flush helpers: the imported `run_bounded` spawns a detached thread per timed-out call, so a permanently blocked sink plus periodic flushes can exhaust threads unless calls are coalesced or limited.

2. **P1 — Python's blocking `log` is missing from the detach requirement.** Design lines 93–96 expose both `try_log` and `log`, then require GIL release only for flush, query, and shutdown. Core `runtime.rs:95` implements `log` using `enqueue_blocking`; under backpressure it can wait indefinitely for queue admission. A straightforward binding following the explicit list can hold the GIL throughout that wait, stopping other Python threads, including a thread intended to initiate shutdown.

   Required: convert Python arguments into owned Rust values while attached, detach for blocking `log` as well as flush/query/shutdown, then reattach to build the result. Define stable queue-full behavior for `try_log`. Test a deliberately blocked writer/full queue while an independent Python thread continues making progress. Do not rely on free-threaded Python to make the supported GIL-enabled builds safe.

3. **P2 — Generated TypeScript declarations do not yet have a defined JSON wire representation.** Design lines 66–86 embed core health and propose exporting versioned DTOs, but do not specify conversion of `u64` counters, arbitrary `serde_json::Value` numbers, platform-sized limits, or paths. Core `health.rs:88` contains multiple `u64` fields and a `PathBuf`. Exporting those counters as JavaScript numbers can silently lose precision above `2^53 - 1`; declaring them as `bigint` does not change JSON parsing. Specta explicitly documents this export hazard and the need for matching serialization: [Specta integer export policy](https://docs.rs/specta/latest/specta/ts/enum.BigIntExportBehavior.html).

   Required before A5.5: choose actual wire encodings, including large event-field integers; define timestamp, optional/null, enum-tag, path, and schema-version behavior; implement explicit DTO conversions. Generate declarations from those wire DTOs and validate actual Rust JSON through the frontend consumer. Include large-number and unknown-version fixtures. Make regeneration-and-diff mandatory even for checked-in output; the design's “checked in or generated-and-diffed” wording currently allows stale declarations.

4. **P2 — The Python object has no locked ownership/concurrency contract or shared-schema dependency.** Design lines 91–101 define an object and prohibit implicit global installation, but do not say whether it owns a direct `Logger`, an `sc-observe::Observability`, or a new reusable nonglobal owner. The A5.2 guard/control redesign is specifically for the installed bridge. Sprint lines 129–132 allow Python implementation after A5.2–A5.3 without depending on the DTO decision in A5.5. Independent implementations can consequently duplicate lifecycle logic and produce incompatible health/error encodings. A mutable PyO3 method racing an immutable method can also produce a borrow-check `RuntimeError` instead of a promised stable observability error; detaching does not remove the object's borrow. See [PyO3 thread-safety guidance](https://pyo3.rs/v0.29.0/class/thread-safety.html).

   Required: name the owned Rust runtime and DTO authority; put the language-neutral wire contract before both bindings; define multiple-instance isolation, concurrent log/query/shutdown outcomes, repeated shutdown, context-manager cleanup, and bounded finalization. Use an explicit synchronization/ownership design and test it from Python threads. Decide supported Python/ABI/platform targets before the binding stage starts, as the design already requests.

5. **P2 — Bridge-owned public health and errors conflict with current normative ownership rules.** Design lines 47 and 66 require a bridge-owned `BridgeHealthReport`; the imported bridge also declares its own `InitError`, `FlushError`, and `ShutdownError`. `docs/requirements.md:94` (TYP-030) explicitly centralizes even crate-specific error enums and concrete health reports in `sc-observability-types`, and `public-api-checklist.md` repeats the rule. Freezing A5-D01–D06 without an explicit ownership decision leaves implementers with incompatible requirements.

   Required in A5.0: either approve a scoped companion-crate exception and update normative docs/checklist, or centralize neutral types with conversions that preserve the core dependency boundary. Record duplicate-name/re-export choices and diagnostic code ownership. Do not move bridge-dependent error payloads into the base crate and accidentally create a dependency cycle.

6. **P2 — Paged query DTOs promise a capability the existing query contract does not define.** Design line 78 promises paged query results. Core `query.rs:44–110` supplies a limit, ordering, timestamp filters, events, and a truncation flag, but no continuation cursor or stable snapshot identity. Advancing by the last timestamp can omit records sharing that timestamp; offsets can repeat or skip records across rotation and retention.

   Required before DTO freeze: either explicitly offer bounded snapshots for v1 or define opaque continuation tokens, tie-breaking, snapshot consistency, and stale-token errors. Test equal timestamps and rotation/retention between pages. Keep application command names in BTIT as planned.

The existing A5-D01 formatter guard fix, exact macro-version pin, subprocess global-install tests, and separation of Tauri/Python dependencies from core are appropriate. Keep BTIT's file-clearing policy local, but make its A5.4 evidence exercise concurrent writes/rotation: a flush followed by truncation is not an exclusive writer barrier.

For the later Python release gate, turn the approved platform matrix into wheel tags/architectures and Linux compatibility targets, and test installation of built wheels in clean environments, not only development imports. Maturin distinguishes wheel building and portable Linux distribution requirements: [Maturin distribution tooling](https://github.com/PyO3/maturin). These packaging choices can remain deferred behind an explicit A5.6 entry gate.

Validation performed: read-only inspection of both plan files, relevant core runtime/query/health and normative API rules, pinned BTIT bridge lifecycle and Tauri integration source, and primary Specta/PyO3/maturin documentation. No implementation changes or executable tests were performed. No prior review's asserted evidence is treated as validation for this review.
